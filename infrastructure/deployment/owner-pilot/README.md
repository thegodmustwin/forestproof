# Owner-only gateway candidate

This uninstalled candidate protects the isolated synthetic owner demo. Caddy binds to VPS loopback and protects all paths with one owner credential. Set `FORESTPROOF_OWNER_GATEWAY_PORT` and `FORESTPROOF_OWNER_WEB_PORT` to distinct free ports, avoiding the existing preview port 13000. The gateway strips the browser Authorization header, replaces the identity assertion headers, checks the origin on unsafe requests and limits request bodies to 2 MB.

Access it only through an authenticated SSH tunnel from the owner's computer to the VPS loopback port. The SSH connection encrypts traffic between machines. HTTP Basic authentication over a public or otherwise untrusted network is unsafe; do not expose this listener publicly or forward it through a public proxy. The API must separately bind only to loopback, and no other host listener may bypass the gateway. The server's local users and privileged processes remain within the trust boundary.

Set `FORESTPROOF_OWNER_SUBJECT` to the same pseudonymous owner identifier on the gateway, web and API. Use 1–63 lowercase ASCII letters, digits, underscores and dashes, starting with a letter. This value is the Basic Auth username and the audit actor. Supply the owner’s bcrypt password hash through Caddy's `FORESTPROOF_OWNER_PASSWORD_HASH` using a protected runtime secret. Generate it privately with the interactive `caddy hash-password` command.

Generate two independent tokens, each with at least 32 random bytes encoded as a URL-safe string. Store them privately and inject `FORESTPROOF_OWNER_GATEWAY_TOKEN` into Caddy and the web process, and `FORESTPROOF_INTERNAL_API_TOKEN` into the web and API processes. Use 43–128 characters from `A-Z a-z 0-9 _ -`. Set `FORESTPROOF_OWNER_GATEWAY_ORIGIN` on the web process to the exact tunnel origin, for example `http://127.0.0.1:18080`. Point the web process at the API's loopback URL. Set API mode and web proxy mode to `owner_demo`.

Caddy gets the subject from its authenticated username. The Next.js proxy verifies the gateway token and configured subject before forwarding to the API. It also checks the exact POST origin. The API verifies the distinct service token and expected subject, then records that subject for review mutations. Both application processes reject requests when their required identity settings are missing or invalid. To revoke the sole owner credential, stop the gateway, replace its password hash and restart it with the new secret. Retain the subject for the same owner so previous events stay attributable. Use a new subject for a new owner and update all three components together. Keep owner credentials and service tokens out of Git, chat and logs.

This credential model is scoped to one owner over the SSH tunnel. The gateway and both application processes require loopback isolation. Existing host users and privileged processes are in the trust boundary. Verify listener isolation and credential rotation in staging before use. The synthetic demo blocks evidence uploads and keeps LIVE disabled. A real pilot still requires separate live storage, recovery, verified source access and an end-to-end acceptance run.

An optional on-demand Copernicus satellite-scene metadata lookup is available only in `owner_demo` when the API process explicitly sets `FORESTPROOF_COPERNICUS_CATALOG_ENABLED=true`. It is disabled by default and the shared preview does not enable it. Results are scene context, not alerts or proof of coverage; the lookup has a 15-minute per-process cooldown and does not download imagery. It has been tested locally but not installed or tested on OVH. Review current terms, network access, host costs and security before deployment.

CI runs test_gateway.sh in an isolated GitHub runner with a synthetic password and mock loopback upstream. It checks that missing credentials fail closed, the gateway requires authentication, untrusted Host headers and cross-origin mutations are rejected, credentials are not forwarded to the upstream, and the listener is loopback-only. These checks passed in GitHub Actions run 40625015460; they do not establish VPS or production security. This CI use of Docker does not require Docker on the owner's laptop.
