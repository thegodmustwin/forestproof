# Owner-only gateway candidate

This Caddy configuration is an **uninstalled pilot candidate**, not a public website configuration. It listens only on VPS loopback and protects all paths with one bcrypt-hashed owner credential. `FORESTPROOF_OWNER_GATEWAY_PORT` and `FORESTPROOF_OWNER_WEB_PORT` must be set explicitly to distinct ports verified free on the host; missing values fail validation. The existing family preview already uses host web port 13000, so do not reuse it. The gateway forwards to the selected loopback web port, strips the Basic authorization header before proxying, rejects unsafe browser requests without the exact tunnel origin, and limits request bodies to 2 MB.

Access it only through an authenticated SSH tunnel from the owner's computer to the VPS loopback port. The SSH connection encrypts traffic between machines. HTTP Basic authentication over a public or otherwise untrusted network is unsafe; do not expose this listener publicly or forward it through a public proxy. The API must separately bind only to loopback, and no other host listener may bypass the gateway. The server's local users and privileged processes remain within the trust boundary.

The bcrypt hash is supplied through FORESTPROOF_OWNER_PASSWORD_HASH using a protected server-side secret mechanism. Caddy must fail to start if the hash is missing. Never put a password or hash in Git or chat. Generate and enter a strong owner password privately on the VPS using Caddy's interactive hash-password command; the test password in test_gateway.sh is synthetic and must never be used outside CI.

The experimental `owner_demo` API mode verifies a separate web-to-API token and records a server-derived `owner` actor; this is service authentication, not person-level authentication. It must use the separately authenticated gateway and isolated loopback web/API listeners. The configuration does not provide individual identities, login revocation, rate limiting, production storage, backups, a verified live provider, or protection for an exposed web/API listener. The application remains synthetic. Before real evidence or deployment, verify those controls, inspect occupied ports and firewall state again, verify the owner workflow over SSH, and document recovery.

CI runs test_gateway.sh in an isolated GitHub runner with a synthetic password and mock loopback upstream. It checks that missing credentials fail closed, the gateway requires authentication, untrusted Host headers and cross-origin mutations are rejected, credentials are not forwarded to the upstream, and the listener is loopback-only. These checks passed in GitHub Actions run 40625015460; they do not establish VPS or production security. This CI use of Docker does not require Docker on the owner's laptop.
